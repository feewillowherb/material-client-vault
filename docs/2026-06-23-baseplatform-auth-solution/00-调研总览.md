# Urban 客户端 BasePlatform 授权方案调研

## 调研背景

UrbanManagement 客户端当前使用简单的字符串验证机制（BuildLicenseNo 和 FdBuildLicenseNo）进行授权。该机制为测试版本授权方式，即将弃用。

正式版的授权方式需要迁移到 BasePlatform，实现：
1. **离线授权**：现场人员使用脚本获取机器码，在 BasePlatform 填入机器码后下载授权文件
2. **在线授权**：通过 BasePlatform 生成的授权码，在客户端输入，然后客户端将当前机器码发送给服务器并持久化

## 调研目标

1. 分析 UrbanManagement 当前授权机制和需要弃用的部分
2. 分析 BasePlatform 现有的授权能力
3. 设计基于 BasePlatform 的离线和在线双授权方案
4. 设计客户端验证机制（离线和在线）

## 调研范围

- **UrbanManagement 项目**：ABP 框架的城管管理系统（需要迁移授权）
- **MaterialClient 项目**：现有的材料客户端
- **FdSoft.BasePlatform**：基础平台服务层
- **FdSoft.BasePlatform.PublicApi**：基础平台公开 API（UrbanManagement 通过此接口通信）
- **FdSoft.BasePlatform.WebApi**：基础平台 Web API（涉及 UI 相关操作）

## 关键发现

### 1. 当前 UrbanManagement 授权机制

#### 1.1 当前验证方式

```csharp
// GovProject 实体定义
public class GovProject : Entity<Guid>
{
    public string ProName { get; set; } = default!;
    public string? BuildLicenseNo { get; set; }        // 建设许可证号
    public string? FdBuildLicenseNo { get; set; }      // 对接码
}
```

**验证逻辑**：
- API 接收端验证 `BuildLicenseNo` 或 `FdBuildLicenseNo`
- 通过字符串匹配查询数据库中的项目信息
- 双重验证：先验证对接码，再验证建设许可证号

**问题**：
- 字符串泄露风险高
- 无机器绑定
- 缺乏过期控制
- 重放攻击风险

#### 1.2 当前 MaterialClient.Urban 客户端授权结构

```csharp
// MaterialClient.Urban 当前 LicenseInfo 结构（保持不变）
public class LicenseInfo
{
    public string LicenseKey { get; set; }          // 许可证密钥（BuildLicenseNo）
    public string? MachineCode { get; set; }       // 机器码（新增字段）
    public DateTime? ExpireDate { get; set; }      // 过期日期（新增字段）
    public string? ProId { get; set; }             // 项目ID（新增字段）
    public string? ProName { get; set; }           // 项目名称（新增字段）
}
```

**当前客户端授权逻辑**：
1. 客户端启动时从本地配置/数据库读取 `LicenseInfo`
2. 使用 `LicenseKey`（即 BuildLicenseNo）调用 UrbanManagement API
3. UrbanManagement 验证 `BuildLicenseNo` 有效性
4. 如果验证成功，客户端可以正常使用

**授权流程调整**（兼容现有客户端结构）：
- 保持 `LicenseInfo` 结构不变
- 新增 `MachineCode`、`ExpireDate`、`ProId`、`ProName` 字段（可选字段）
- UrbanManagement 在 GovProject 中扩展授权字段（MachineCode、AuthToken 等）
- 客户端验证时通过 `LicenseKey`（BuildLicenseNo）+ `MachineCode` 向 UrbanManagement 验证

### 2. BasePlatform 现有授权能力

#### 2.1 授权码获取 API

**位置**：`FdSoft.BasePlatform.PublicApi/Controllers/AuthClientLicenseController.cs`

```csharp
[AllowAnonymous]
public class AuthClientLicenseController : BaseController
{
    [HttpPost]
    public IActionResult GetAuthClientLicense([FromBody] AuthClientLicenseDTO authClientLicense)
    {
        string key = $"{RedisConst.AuthClientLicense}:{authClientLicense.productCode}:{authClientLicense.code}";
        string license = RedisHelper.Get(key);
        RedisHelper.Del(key); // 一次性授权码
        if (!string.IsNullOrEmpty(license))
        {
            result.success = true;
            result.data = license;
            return JsonDate(result);
        }
        return JsonDate(result.Fail("授权码未获取到授权信息"));
    }
}
```

**特点**：
- 基于 Redis 的临时授权码
- 一次性使用（使用后删除）
- 产品码 + 授权码 双重验证

### 离线授权流程设计

**步骤**：
1. 现场人员运行机器码获取脚本
2. 脚本生成当前机器的唯一机器码
3. 在 BasePlatform 管理界面填入机器码
4. BasePlatform 生成授权文件（包含机器码、AuthToken、过期时间）
5. 下载授权文件到本地
6. 客户端导入授权文件，写入 SQLite
7. 客户端启动时验证机器码一致性

### 在线授权流程设计

**步骤**：
1. 管理员在 BasePlatform 生成授权码（写入 Redis）
2. 将授权码提供给客户端用户
3. 客户端输入授权码
4. 客户端获取当前机器码
5. 调用 BasePlatform API：
   - 验证授权码
   - 上报机器码
   - BasePlatform 持久化到 Material_MachineCode
6. 客户端将授权信息写入 SQLite
7. 客户端启动时验证机器码一致性

### AuthType 设计

```csharp
public enum AuthType
{
    Offline = 0,  // 离线授权（文件导入）
    Online = 1    // 在线授权（授权码激活）
}
```

### 客户端验证机制

**离线验证**（每次启动）：
1. 从 SQLite 读取授权信息
2. 获取当前机器码
3. 比对当前机器码与数据库中的机器码
4. 如不一致，提示"授权无效，请联系管理员"并关闭程序
5. 检查授权过期时间

**在线验证**（定期或手动触发）：
1. 从 SQLite 读取授权信息
2. 获取当前机器码
3. 调用 BasePlatform API 验证
4. 比对：当前机器码 == SQLite 机器码 == BasePlatform 机器码
5. 如不一致，提示"授权无效，请联系管理员"并关闭程序

## 风险与应对

| 风险 | 影响 | 应对措施 |
|-----|------|---------|
| 机器码不稳定 | 授权失效 | 使用多重硬件特征，提供机器码重新绑定流程 |
| SQLite 被篡改 | 绕过授权 | 加密存储，增加校验和 |
| 离线环境无法联网 | 无法在线验证 | 支持纯离线模式，仅本地验证 |
| 授权文件泄露 | 被滥用 | 授权文件绑定机器码，定期在线验证 |
| 网络中断影响在线验证 | 用户体验差 | 支持离线宽限期，缓存验证结果 |
