## 错误 1（严重）：`RecycleTransportRecord.FromWeighingRecord` 方法签名与语义错误

### 问题

§2.2 发料 DTO 的静态工厂方法名为 `FromWeighingRecord`，第一个参数为 `WeighingRecord record`，但 **Recycle 同步链路的唯一数据来源是 Waybill**，与 WeighingRecord 无关。

### 代码位置

`MaterialClient.Recycle/Models/RecycleTransportRecord.cs` 第 92-98 行：

```csharp
public static RecycleTransportRecord FromWeighingRecord(
    WeighingRecord record,    // ← 错误：不应依赖 WeighingRecord
    Waybill? waybill,
    string outPhotos,
    string productName,
    string? pointNumber,
    string? carrierCompanyName = null)
```

### 调用方

`RecycleDataSyncService.SubmitSendingAsync` 第 184-194 行被迫构造一个**空壳 WeighingRecord**：

```csharp
var payload = RecycleTransportRecord.FromWeighingRecord(
    new WeighingRecord // 不使用 WeighingRecord 字段，仅用 Id 作为 fallback
    {
        Id = waybill.Id,
        AddDate = waybill.AddDate
    },
    waybill,
    photos,
    materialName,
    _options.PointNumber,
    carrierCompanyName);
```

### 具体错误点

| # | 错误 | 说明 |
|---|------|------|
| 1a | **方法名错误** | `FromWeighingRecord` 暗示以 WeighingRecord 为主数据源，实际所有业务字段来自 Waybill |
| 1b | **参数签名错误** | `WeighingRecord record` 参数不应存在；Recycle 同步链路不涉及 WeighingRecord |
| 1c | **`dataNo` fallback 逻辑违反设计** | `FromWeighingRecord` 内部第 104-106 行：OrderNo 为空时回退为 `$"R-{record.Id}"`，但设计定稿（task 5.6）明确要求 **OrderNo 为空时跳过上报，不用 R-{id} 回退**。`RecycleDataSyncService.ProcessWaybillAsync` 第 127 行已正确实现跳过逻辑，但 DTO 层仍保留了这个 fallback，是矛盾的 |
| 1d | **`carNo` fallback 逻辑不当** | 第 107-109 行：`waybill.PlateNumber` 为空时回退到 `record.PlateNumber`，但 record 是空壳对象，PlateNumber 始终为 null，这个 fallback 永远不会生效 |
| 1e | **`outTime` fallback 逻辑不当** | 第 103 行：`waybill.OutTime` 为空时回退到 `record.AddDate`，但 record.AddDate 只是被赋值为 waybill.AddDate，等效于直接用 waybill.AddDate |

### 与 §2.3 的对比

`RecycleMaterialTransportRecord.FromWaybill`（§2.3 收料 DTO）的签名**完全正确**——只接收 `Waybill waybill`，不涉及 WeighingRecord：

```csharp
public static RecycleMaterialTransportRecord FromWaybill(
    Waybill waybill,
    string inPhoto,
    string materialName,
    string? carrierCompanyName,
    string? pointNumber)
```

§2.2 的 `RecycleTransportRecord` 应与 §2.3 保持一致。

### 修复建议

1. 将 `FromWeighingRecord` 重命名为 `FromWaybill`
2. 移除 `WeighingRecord record` 参数
3. 移除 `dataNo` 的 `$"R-{record.Id}"` fallback（OrderNo 为空的情况由调用方 `ProcessWaybillAsync` 跳过）
4. 移除 `carNo` 和 `outTime` 对 WeighingRecord 字段的 fallback
5. 签名对齐为：`FromWaybill(Waybill waybill, string outPhotos, string productName, string? pointNumber, string? carrierCompanyName)`
6. 更新 `RecycleDataSyncService.SubmitSendingAsync` 调用点，去掉 `new WeighingRecord { ... }` 构造

## 错误 2（中等）：`RecycleDataSyncService.GetPendingWaybillsAsync` 全量加载后内存过滤

### 问题

第 98-120 行的 `GetPendingWaybillsAsync` 先从数据库加载**所有** Recycle + Completed 的 Waybill，然后在内存中通过 `RecycleSyncStateStore` 过滤已同步/已放弃的记录。

### 代码位置

```csharp
// 第 103-106 行：全量查询
var waybills = await queryable
    .Where(w => w.WeighingMode == WeighingMode.Recycle)
    .Where(w => w.OrderType == OrderTypeEnum.Completed)
    .ToListAsync(cancellationToken);

// 第 111-119 行：内存过滤
return waybills
    .Where(w =>
    {
        var status = RecycleSyncStateStore.GetWaybillSyncStatus(w);
        if (status == SyncStatus.Synced) return false;
        return RecycleSyncStateStore.GetWaybillFailCount(w) < maxFail;
    })
    .ToList();
```

### 影响

- 同步状态存储在 `Waybill.ExtraProperties`（JSON 列），EF Core SQLite 无法直接在 SQL 层面过滤 JSON 字段内的特定键值
- 当 Waybill 数量增长后，每次同步周期都会全量加载所有 Recycle + Completed 记录到内存
- 对于工业环境 7×24 运行、定时轮询同步的场景，这是潜在的性能瓶颈

### 说明

这不是一个"bug"，而是 SQLite + ExtraProperties 架构下的**固有限制**。当前实现在数据量小（< 1000 条）时不会出现问题。如果后续数据量增长显著，应考虑：
- 为同步状态增加专用的数据库列（而非 ExtraProperties）
- 或使用 SQLite JSON1 扩展在 SQL 层面过滤

## 错误 3（低）：tasks.md 4.3 任务描述与实际实现不一致

### 问题

`tasks.md` 第 26 行：

> 4.3 更新 `RecycleTransportRecord.FromWeighingRecord`：`dataNo`=OrderNo、`carrierCompanyName`、移除 ProductName 配置依赖

该任务描述仍引用 `FromWeighingRecord`，应改为 `FromWaybill`（与 4.1 中 `RecycleMaterialTransportRecord.FromWaybill` 命名一致）。同时该任务标记为 `[x]` 已完成，但方法实际上仍叫 `FromWeighingRecord`。

## 错误总结

| # | 严重度 | 文件 | 问题 | 修复类型 |
|---|--------|------|------|----------|
| 1a | **严重** | `RecycleTransportRecord.cs` | 方法名 `FromWeighingRecord` 应为 `FromWaybill` | 重命名 |
| 1b | **严重** | `RecycleTransportRecord.cs` | 不应接收 `WeighingRecord` 参数 | 改签名 |

| 1d | 低 | `RecycleTransportRecord.cs` | `carNo` fallback 到空壳 WeighingRecord.PlateNumber 无意义 | 删除 fallback |
| 1e | 低 | `RecycleTransportRecord.cs` | `outTime` fallback 等效于 `waybill.AddDate`，绕了一圈 | 简化 |
| 2 | 中等 | `RecycleDataSyncService.cs` | 全量加载 + 内存过滤，潜在性能问题 | 架构优化（非紧急） |
