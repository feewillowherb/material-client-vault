# MaterialClient.Urban 设备同步与状态监控解决方案调研

## 调研范围

本次调研针对 MaterialClient.Urban 与 UrbanManagement 之间的实时数据同步、设备状态监控和错误日志提交提供完整解决方案。

### 核心问题
1. **设备信息实时同步**：如何将 MaterialClient.Urban 中的设备信息实时同步到 UrbanManagement
2. **在线状态监控**：客户端和摄像头在线情况的实时监控方案
3. **错误日志提交**：Urban 需要把错误日志提交到服务器的方案

### 方案范围（已定）

本系列**仅采用 WebSocket 长连接**承载设备状态、心跳与错误日志上行；**不采用** HTTP 定时轮询、HTTP 长轮询、混合降级，以及错误日志的独立 HTTP 批量上传通道。

**应用层实现（已定）**：使用 **ASP.NET Core SignalR**——服务端 `Volo.Abp.AspNetCore.SignalR`，客户端 `Microsoft.AspNetCore.SignalR.Client`（桌面端不引用 AspNetCore.SignalR 包）。详见 [05-SignalR技术选型与集成.md](./05-SignalR技术选型与集成.md)。

称重记录仍沿用现有 **Refit HTTP**（`POST /api/urban/weighing-records`），与 SignalR Monitor 通道职责分离。

**错误日志带宽（相对上行总量）**：在仅长连接前提下，平稳期以心跳为主，错误日志占比通常较低；故障爆发期单连接上错误帧占主导。不再与 HTTP 轮询/批量上传方案做并列对比。

### Monitor 可选性与默认策略（已定）

| 项目 | Monitor 默认 | 说明 |
|------|--------------|------|
| **MaterialClient**（通用宿主） | **关闭** | `appsettings` 中 `DeviceMonitoring:Enabled = false`；实现保留在 Common/Urban 模块，按需打开 |
| **MaterialClient.Urban** | **开启** | 城管场景默认 `Enabled = true`（可在工地配置中关闭） |
| **UrbanManagement** | 始终提供 Hub/API | 接收端能力常驻；无心跳客户端显示为「未启用监控」或「离线/未知」，**不拒绝**称重 HTTP |

**总开关**：客户端 `appsettings.json` → `DeviceMonitoring:Enabled`（`bool`）。为 `false` 时不建立 SignalR 连接、不启动心跳、摄像头探测及经 Monitor 通道的远程错误日志推送。

**故障隔离（必须）**：

- **核心路径**：称重采集、本地 SQLite、`UrbanServerUploadService` → `POST /api/urban/weighing-records` **不依赖** Monitor。
- Monitor 内异常仅写本地 Serilog，**不得**阻塞 UI 主流程或导致应用无法启动。
- SignalR 断线、心跳失败、海康 SDK 探测失败 → 仅影响可观测性数据，**不影响**称重上传成功/失败判定。
- 远程错误日志为附加能力：依赖 `DeviceMonitoring:Enabled` 且 `ErrorLogging:EnableRemoteLogging`；关闭时仍保留本地 `Logs/` 文件。

详见 [02-状态监控方案.md](./02-状态监控方案.md) §Monitor 隔离、[04-实施建议.md](./04-实施建议.md) §配置与模块注册。

## 相关项目

- **MaterialClient**: 通用称重客户端宿主；**Monitor 默认关闭**，实现可共用，由 `DeviceMonitoring:Enabled` 启用
- **MaterialClient.Urban**: 城管称重客户端；**Monitor 默认开启**，负责本地称重与可选上云监控
- **UrbanManagement**: ABP 框架的服务端应用，接收和处理城管称重数据
- **MaterialClient.Common**: 共享组件库，包含 Monitor 相关接口与实现（如摄像头探测）

## 现有架构分析

### MaterialClient.Urban 端

**核心组件**:
- `UrbanServerUploadService`: 负责将称重记录提交到 UrbanManagement 服务端
- `IUrbanManagementApi`: 基于 Refit 的 RESTful API 接口
- `UrbanWeighingExtensionService`: 管理称重记录的同步状态和扩展信息

**数据模型**:
- `UrbanWeighingExtension`: 存储同步状态、重试次数、异常标志等
- `WeighingRecord`: 本地称重记录主表
- `SyncStatus` 枚举: Pending (待上传)、Synced (已同步)、Failed (上传失败)

**通信机制**:
- 基于 Refit 的 HTTP 客户端
- POST `/api/urban/weighing-records` 提交称重记录
- JSON 格式数据传输
- 使用 `ClientRecordId` 进行幂等性控制

### UrbanManagement 端

**核心组件**:
- `UrbanWeighingRecordController`: 接收称重记录的 API 控制器
- `UrbanWeighingRecordAppService`: 处理称重记录的业务逻辑
- `FileService`: 处理文件上传和管理

**数据模型**:
- `UrbanWeighingRecord`: 服务端称重记录表
- `UrbanWeighingRecordAttachment`: 称重记录附件关联表
- `AttachmentFile`: 文件存储表

**数据库设计**:
- SQLite 存储
- `ClientRecordId` 唯一索引用于去重
- 支持附件关联存储

### 当前同步流程

1. **称重记录创建**: MaterialClient.Urban 创建称重记录时生成 `UrbanWeighingExtension`
2. **后台上传**: 后台服务查询待上传记录并调用 API 提交
3. **状态更新**: 根据上传结果更新 `SyncStatus`、`RetryCount`、`LastErrorTime`
4. **服务端处理**: UrbanManagement 接收数据，通过 `ClientRecordId` 去重，存储到数据库

## 关键发现

### 优势
- ✅ 已有基础的同步框架和 API 通信机制
- ✅ 支持同步状态跟踪和错误处理
- ✅ 服务端有完善的数据模型和去重机制
- ✅ 支持 ABP 框架，便于扩展新功能

### 限制和挑战
- ⚠️ 当前仅支持称重记录的批量同步，缺乏实时性
- ⚠️ 没有设备状态监控的专用机制
- ⚠️ 错误日志仅在本地存储，未集中到服务端
- ⚠️ 缺乏心跳和在线状态检测机制
- ⚠️ 服务端缺少设备管理界面

### 技术债务
- 需要建立 **SignalR** 实时通信（单 Hub、多方法；传输为 WebSocket）
- 需要设计设备状态数据模型
- 需要实现错误日志经长连接的远程传输和存储
- 需要考虑服务端的高可用性和负载均衡（连接保活、重连、Hub 扩展）
