## 2. 风险矩阵

### 2.1 阻断性风险

| 风险 | 等级 | 影响 | 缓解措施 | 状态 |
|------|------|------|---------|------|
| ~~接口文档缺失~~ | ~~**阻断**~~ | ~~无法确定请求/响应格式~~ | ~~已从 MaterialMonospec 获取~~ | ✅ **已解决** |
| HMAC-SHA256 签名密钥缺失 | **阻断** | 无法构造认证 Header | **需从平台方获取 accessKey + secretKey** |
| `pointNumber`（厂标识）缺失 | **阻断** | 请求体必填字段无法填充 | **需从运营方获取各厂唯一标识** |
| `productName`（成品名称）缺失 | **阻断** | 请求体必填字段无法填充 | **需确认与称重记录的映射关系** |

### 2.2 技术风险

| 风险 | 等级 | 影响 | 缓解措施 |
|------|------|------|---------|
| 外部接口不可达（网络/防火墙） | 中 | 数据无法上报 | 网络检测 + 重试 + 离线暂存 |
| 外部接口响应格式不稳定 | 中 | 同步状态判断错误 | 严格按文档 `code == 200` 判断，添加日志 |
| HMAC-SHA256 签名实现偏差 | 中 | 认证失败 | 提前实现签名测试工具，对照文档验证 |
| 图片 Base64 过大超出接口限制 | 中 | 上报失败 | 复用 `CompressImage` 压缩逻辑，确认接口限制 |
| 接口无幂等性 | 低 | 重复提交导致数据重复 | 使用 `DataNo` 唯一标识作为幂等键 |
| ProductCode 5020 与已有产品冲突 | 低 | 授权/配置混乱 | 确认 5020 不与现有 ProductCode（5000/5010/5030）重复 |
| 重量精度问题（kg→吨） | 低 | 业务数据偏差 | 使用 `decimal` 保持精度，÷1000 |

### 2.3 架构风险

| 风险 | 等级 | 影响 | 缓解措施 |
|------|------|------|---------|
| Common 层改动影响已有客户端 | 中 | 5000/5001/5010 回归问题 | 仅新增枚举成员，不改已有接口，向后兼容 |
| Recycle 模块耦合 Common 层内部实现 | 低 | 升级困难 | 通过接口/抽象隔离，使用 DI 注入 |
| 配置混淆（多个同步目标共存） | 低 | 运维错误 | 配置命名空间隔离（`RecycleSync:` 前缀） |

## 6. 总结

**MaterialClient.Recycle（ProductCode 5020, WeighingMode 301）** 的核心工作量在于：

1. **新增枚举成员**（`WeighingMode.Recycle = 301`、`ProductCode.Recycle = 5020`）—— Common 层最小改动
2. **新增客户端模块**（`MaterialClient.Recycle`），复用 Common 层全部能力
3. **实现 HMAC-SHA256 签名认证**（§2.2 接口强制要求，与现有认证方式不同）
4. **替换数据上报接口**（从 `SynchronizationOrderAsync` → §2.2 批量接口，JSON Array + Base64 内嵌图片 + kg→吨转换）
5. **注册 ProductCode 5020**（BasePlatform 授权体系）
6. **配置 WeighingMode 路由**（启动时选择加载 Recycle 模块）

**已解决的关键缺口**：§2.2 接口文档已获取、`SynchronizationOrderAsync` 定义已确认、WeighingMode 枚举已确认。**当前阻断项**为 HMAC 密钥、pointNumber、productName 等运营侧配置值。
